One install package for Pintail

Plan SPEC.md Tracking acme/pintail#412

Pintail, a self-hosted feature-flag service, ships as three Helm charts and depends on cert-manager without saying so: the install succeeds, the first FlagSet fails. This plan makes the existing pintail-server chart the one install package and removes the hidden runtime prerequisite with a self-signed webhook certificate. No new chart, CLI or controller.

Worked example. Pintail and every repository, path and issue cited here are fictional, invented to show the template's workflow. The ground-truth and contrarian evidence is illustrative and says so.

1 Problem

Three charts, one undocumented prerequisite, and a product that breaks on first use.

An operator installs pintail-crds, then pintail-server, then pintail-console. The server's admission webhook validates every FlagSet and fails closed; its TLS certificate comes from cert-manager. On a cluster without cert-manager the chart silently skips the certificate, the webhook listener never starts, and the first kubectl apply of a FlagSet fails.

Runtime prerequisite. Something that must already be running in the cluster for the product to work after an install that succeeded without it; hidden when the install neither provides, checks nor documents it. Sharpened in grill session 1, Q3.

2 Solution

pintail-server becomes the install package: one helm install on a bare cluster yields the whole product.

Moving partWhat changes
webhook certificate

New default source self-signed: the server generates the certificate, stores it in a Secret and injects the CA into its own webhook configuration. cert-manager stays an opt-in source.

console

Already embedded in the server; console.enabled flips to true.

CRDs

The server already applies its own CRDs at startup; the manual step and the pintail-crds chart retire.

old charts

One final release each that makes leaving them safe, then deprecation.

3 User stories

  • Operator, fresh cluster. One helm install gives the whole product; the webhook works without cert-manager; a green install means a working product.
  • Operator with cert-manager. Keeps issuing the webhook certificate through it.
  • Operator, day 2. Evaluations keep flowing during certificate rotation; every replica serves the same certificate; CRD changes arrive with the server upgrade.
  • Operator, console. Reachable after install without a second chart, and off with one value.
  • Operator on the three-chart layout. A documented migration that keeps every FlagSet, announced by the deprecated charts themselves.
  • Flag author. Validation behaves exactly as before.
  • Security reviewer. The self-signed CA is scoped to the webhook Service only, and the server may patch only its own webhook configuration.
  • Maintainer. One chart, one release process, one install guide, and an acceptance test that stops a hidden runtime prerequisite from coming back.

The full numbered list (16 stories) is in SPEC.md.

4 Implementation decisions

DecisionRationale
no umbrella chart

pintail-server already carries server, Service, webhook and console switch. Dropped after the contrarian's first pass.

certificate.source: self-signed

A third value of the existing webhook.certificate.source enum, and the new default. cert-manager and secret are unchanged. (Ground truth corrected the value's name.)

no bundled cert-manager

Recommended by the agent, overruled by the human: cert-manager is a cluster-wide singleton, and one certificate for one Service does not justify shipping it.

failurePolicy: Fail

Kept. Readiness includes the webhook listener, so the API server reaches only pods that can validate; flag evaluation does not wait.

scoped RBAC

One Secret; one webhook configuration by resourceNames. Not rendered in the other two modes.

loud guard

source: cert-manager without the cert-manager API fails the render with the value to change.

console.enabled: true

Default flip only; no new component.

5 Migration from the three-chart layout

pintail-crds renders its CRD from templates/: uninstalling an earlier release deletes every FlagSet.

  1. Upgrade pintail-crds to its final release, which adds helm.sh/resource-policy: keep to the CRD.
  2. Upgrade pintail-server with the console on.
  3. Uninstall pintail-console; it holds no state.
  4. Uninstall pintail-crds; the CRD and every FlagSet stay.

6 Testing decisions: the test gate

The plan is done when these three scenarios pass in CI on pintail-server main. Nothing less, and nothing else required.

seam: helm install/upgrade/uninstall + kubectl FlagSet + HTTP API # the only one
  1. Bare cluster. kind, no cert-manager, no values. A valid FlagSet is accepted, an invalid one rejected with its message, a flag evaluates, the console answers 200. With two replicas, ten consecutive applies all succeed.
  2. cert-manager present. source: cert-manager: same assertions, the CA matches the issued certificate, no self-signed Secret. Same value without cert-manager: the install fails with the guard's message.
  3. Migration. Old layout with five FlagSets, documented order applied: all five still evaluate unchanged, helm list shows one Pintail release, the console answers 200.
One exception below the seam. Certificate renewal depends on time. The certificate module gets unit tests with an injected clock for two behaviours only: renewal after the threshold, and two concurrent renewals yielding one certificate.

A good test fails if a user would notice, and only then. Prior art: the server's existing kind-based end-to-end suite, which the scenarios extend.

7 Scope

In scope

  • Self-signed certificate source, as the default.
  • Loud guard for the cert-manager source.
  • Console on by default.
  • Final releases of the two retiring charts.
  • Docs: one-command install guide, a Certificates page, a rewritten troubleshooting entry.
  • Three acceptance scenarios plus the renewal unit tests.

Out of scope

  • Any new controller, operator or CLI.
  • Bundling cert-manager, in any form.
  • Changes to validation rules or the evaluation API.
  • GitOps installs: not prevented, not tested.
  • Archiving the old repositories: two server minor releases later.
