# Grill session: one install package for Pintail

- **Date:** 2026-09-22
- **Plan:** example-plan
- **Topic:** the seed from acme/pintail#412, "Pintail should install with one command"
- **Note:** fictional worked example. Pintail and every path below are invented for the template.

## Q1: Who is the install for, and what does "it worked" mean to them?

Recommended: the operator of a cluster that runs nothing Pintail-related yet, and "it
worked" means a `FlagSet` is accepted and a flag evaluates, not that `helm install` exits 0.

**Answer:** Agreed. The epic came from three support threads where `helm install` was green
and the first `FlagSet` failed. Success is measured at first real use.

**Resolution:** the acceptance bar is first real use (a `FlagSet` accepted, a flag
evaluated, the console reachable), not install exit status. Carried into the spec's test
gate.

## Q2: What does "one install" mean: one command, one chart, or one Helm release?

The seed says "one package". That could be a single `helm install` that still creates
several releases (an umbrella with hooks), a single chart, or a script that runs three
installs. Recommended: one chart, one release. "One command" alone would admit a wrapper
script, which just hides the three charts.

**Answer:** One chart, one release. A wrapper script is what users already write themselves.

**Resolution:** the term is **Install package**, meaning the one versioned chart an
operator installs to get the whole product, producing exactly one Helm release.

**Glossary updated:**

```md
### Install package

The one versioned chart an operator installs to get the whole product, producing exactly
one Helm release.
_Avoid_: bundle, umbrella, distribution
```

## Q3: You called cert-manager a "dependency". A chart dependency, or something else?

The glossary has no entry for either, and "dependency" is overloaded: in Helm it means an
entry in `Chart.yaml` that Helm installs for you. cert-manager is nothing of the sort here.
The server chart does not list it; it only renders a `Certificate` when the cert-manager API
happens to be served (checked: `charts/pintail-server/templates/certificate.yaml:1`), and
the webhook fails closed without it. Recommended term: **Runtime prerequisite**, with
"hidden" meaning the install neither provides it, checks it, nor documents it.

**Answer:** Yes. And sharpen it: a runtime prerequisite is only hidden if the install
*succeeds* without it. If the chart failed the render, it would be a documented
prerequisite with a bad error message, which is a different (smaller) problem.

**Resolution:** term sharpened as the user stated. The plan's core problem is restated as:
cert-manager is a hidden runtime prerequisite of the webhook.

**Glossary updated:**

```md
### Runtime prerequisite

Something that must already be running in the cluster for the product to work after an
install that succeeded without it; hidden when the install neither provides, checks nor
documents it.
_Avoid_: dependency (reserved for Helm chart dependencies), requirement
```

## Q4: How does the webhook get its certificate on a cluster without cert-manager?

Options:

1. Bundle cert-manager as an optional chart dependency, enabled by default, disabled with
   one value on clusters that already run it.
2. The server generates a self-signed certificate itself and injects the CA into its own
   webhook configuration; cert-manager stays an opt-in source.
3. Keep cert-manager required, but make the chart fail the render when it is missing.

Recommended: (1). It reuses a mature component, rotation is solved, and operators who
already run cert-manager set one value.

**Answer:** Overruled, option 2. cert-manager is a cluster-wide singleton: it owns its CRDs,
its own webhook and every `Certificate` in the cluster. Bundling it means a second copy on
every cluster that already has one when somebody forgets the value, CRD ownership fights
between the two releases, and `helm uninstall pintail-server` taking down the certificate
machinery that other workloads rely on. We need one certificate for one Service name.
That does not justify shipping a cluster-wide controller. Option 3 is still worth having
for the `cert-manager` source: if someone selects it, fail loudly.

**Resolution:** recommendation overruled. Decided: self-signed mode generated by the
server is the default; cert-manager remains an opt-in source; selecting it on a cluster
without cert-manager fails the render with a message (option 3, scoped to that source).
Trade-off accepted: Pintail now owns certificate generation and renewal code, which must be
tested (see Q10 in session 2).

## Q5: Should the webhook keep failing closed?

With self-signed mode there is a window at first start where no certificate exists yet.
Option: switch `failurePolicy` to `Ignore` so that window cannot block `FlagSet` writes.
Recommended: keep `Fail`, and gate the pod's readiness on the webhook listener instead, so
the API server only reaches pods that can validate.

**Answer:** Keep `Fail`. An invalid `FlagSet` that slips in during the window is worse than
a write that is retried.

**Resolution:** `failurePolicy: Fail` stays; readiness includes the webhook listener; flag
evaluation does not wait for the certificate.

## Q6: How are CRD upgrades handled in one chart?

Fact looked up: the `pintail-crds` README (`README.md:14-22`) documents a manual
`kubectl apply` of the CRDs before every server upgrade, because the chart renders them from
`templates/`. Recommended: the new install package carries the CRDs in its `crds/`
directory and a pre-install hook applies updated CRDs on upgrade.

**Answer:** Agreed.

**Resolution:** carried into the first spec draft. (Superseded in session 2: the contrarian
found the README stale; the server already manages its CRDs.)

## Q7: What shape does the install package take?

Given Q2 (one chart) and three existing charts, recommended: an umbrella chart `pintail`
that depends on `pintail-crds`, `pintail-server` and `pintail-console`, plus a thin
`pintailctl install` wrapper that runs preflight checks and prints what is missing.

**Answer:** Umbrella yes. The wrapper too, if it is small.

**Resolution:** carried into the first spec draft. (Superseded in session 2, after the
contrarian's SIMPLIFY.)
